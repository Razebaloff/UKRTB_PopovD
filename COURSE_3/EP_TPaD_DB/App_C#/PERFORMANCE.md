## Хаотичное оседание инея и трещины вокруг шайб — 03.11.2026

## Регистрация через SQLite/SMTP и трещины вокруг кнопки «НАЗАД» — 03.11.2026

Подключены Microsoft.Data.Sqlite 10.0.14 и MailKit 4.18.2.
HockeyUserDatabase создаёт Users в профиле пользователя
Windows, сохраняет уникальные Login/Email, соль, PBKDF2-хеш,
количество итераций и время регистрации. Конфиденциальный
пароль и шестизначный код не сохраняются в текстовом виде.
HockeyAccountService управляет OTP, ограничениями времени/попыток,
сбросом состояния при изменении полей и реальной доставкой
кода через SMTP с STARTTLS/SSL. Вход теперь сверяет пароль
с БД, затем требует email-OTP. При невозможности подключиться
к SMTP или SQLite приложение сообщает об ошибке без
фиктивной успешной регистрации.

JerseyDrawing и SceneSurfaceCache поддерживают 4 поля на
втором этапе регистрации. Form1 связывает оба этапа, управляет
разметкой, Tab-навигацией и переходом к входу после вставки
в SQLite. AccountChecks — изолированные проверки хранилища
и OTP со специальным тестовым отправителем без реального SMTP.

CapsuleCrackDrawing формирует кэшируемую ветвящуюся текстуру
трещин вокруг овальной кнопки «НАЗАД», а CapsuleButton
использует переход FrostHoverAnimation 900 мс, чтобы
постепенно открывать узор. Form1 рисует внешний слой
под кнопкой, без голубой плёнки на её поверхности.

WinForms, фактические FPS, доставка письма и новые тесты
пока не запускались в Windows из текущей рабочей среды.

## Демонстрационные коды без SMTP и сохранение пользователей в SQLite — 03.11.2026

По последнему запросу пользователя подтверждение почты временно
отменено для обоих сценариев: регистрации и входа. Текущий
`HockeyAccountService` по умолчанию включает
`DemoVerificationEnabled = true`. При переходе на второй этап
почтовый сервис не вызывается и не требуется конфигурация SMTP.
Поле кода принимает любую непустую строку и не ограничено шестью
цифрами. Это сохраняет двухшаговый интерфейс, но не подтверждает
почту. UI прямо показывает, что письмо не отправлялось.

База `%LOCALAPPDATA%\\TerritoriyaHokkeya\\users.db` не является
заглушкой: регистрация вызывает `HockeyUserDatabase.InsertAsync`,
SQL сохраняет уникальный логин, почту, соль и PBKDF2-хеш.
Вход продолжает проверять пароль через `VerifyLoginAsync`.
`AccountChecks.cs` дополнен проверкой деморежима без вызова почты,
создания реальной SQLite-записи после любого непустого кода,
отказа при пустом коде и отказа при неправильном пароле.
Отдельные тесты реального OTP сохранены с `demoCodeMode:false`.

Данный режим исключительно для локального прототипа. Включение
реального SMTP позже потребует отдельной проверки безопасности,
лимитов и доставки. Приложение не проходило Windows-сборку и
интерактивные испытания в текущей среде.

## Повторное использование анимации входа после регистрации — 03.11.2026

LoginSuccessDrawing принимает флаг `registration` и динамически
выбирает `JerseyDrawing.InputBounds(true, true)` с четырьмя полями,
границами регистрационной кнопки и статусной строки. Для обычного
входа остаётся старый набор: три поля, кнопка входа, rememberCheck,
«НАЗАД» и статус. Рендер снежного ветра, снежной пыли,
рассеивания пикселей, свечения логина и его переноса на майку
общий, а не две расходящиеся реализации.

Form1.StartSuccessAnimation централизует CaptureScreen, копию
очищенной майки, подготовку текстуры, создание LoginSuccessDrawing
и общий successTimer. После SQLite CompleteRegistrationAsync
вместо NavigateAsync(Login) запускается этот же компонент
с `registration:true`. Preload добавлен для Registration+CodeRequested+
CleanJersey и Menu, чтобы не подготавливать тяжелую сцену после
завершения записи в БД.

Form1.CompleteLoginAnimation восстанавливает состояние сессии,

пользователя в меню вместо повторной регистрации.

Реальную плавность анимации, визуальную идентичность и итоговые
переходы нужно проверить в Windows. .NET/WinForms здесь нет.

## Демовход и новая недельная сетка расписания — 03.11.2026

Form1 для ветки Login вызывает `HockeyAccountService.RequestDemoLoginAsync`
при активном `DemoVerificationEnabled`. Этот метод обходит
`VerifyLoginAsync` и открывает формальный этап кода без SMTP;
проверка логина/пароля по БД остаётся в отдельном методе
для будущего возврата настоящей аутентификации. Регистрация
с SQLite, PBKDF2 и автоматической снежной анимацией остаётся
без изменений. Текущий демонстрационный вход не защищён.

Новый экран AppScreen.Schedule доступен из Entry и Menu.
Form1 хранит исходный экран в `scheduleReturnScreen`,
поэтому кнопка «НАЗАД» и Esc возвращают туда. ScheduleBoard —
один Control с двойной буферизацией, отдельной отрисовкой
недельной таблицы в координатах 1380×600 и кликабельными
выборами недели/дня/слота; на каждый кадр таймера таблица
не перерисовывается. Страница получает фокус через Tab;
стрелки и PageUp/PageDown изменяют выбранные даты.

Чистая модель TrainingSchedule генерирует ровно 11
`TrainingSlot`: время начала 08:00, длительность 60 мин,
время подготовки между занятиями 10 мин, закрытие 21:00.
Последнее занятие 19:40–20:40. Отдельные записи перерывов
и какие-либо «выдуманные бронирования» не создаются.
Тесты StateChecks проверяют длительности, границы и
10-минутные паузы; AccountChecks дополнен сценарием
демовхода без записи фальшивых пользователей в SQLite.

F12 для Schedule сохраняет текущую интерактивную сцену
как PNG размера окна; статический CLI 32K-экспорт
расписания пока не заявлен. Проверка исходников и GitHub
не заменяет реальный запуск WinForms в Windows.
